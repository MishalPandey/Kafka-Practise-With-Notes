1--> What is Apache Kafka?
     --> Apache Kafka is an open-source distributed event streaming platform.
	 
	 
2-> Let's break Open-source, Distributed Event Streaming Platform into four simple parts.
     --> 
		1. Open-source
			- Kafka's source code is publicly available.
			- Developers can use, modify, and contribute to Kafka.
			- It is free to use under its open-source license.

		In simple words: Anyone can use Kafka and contribute to its development.

		2. Distributed
			- Kafka runs across multiple servers called Brokers.
			- Data is distributed across these servers.
			- If one broker fails, Kafka can still operate using replicated data on other brokers.

		In simple words: Instead of depending on one server, Kafka uses multiple servers to handle data, improving scalability and fault tolerance.

		3. Event
			An event is simply a record of something that happened in an application.
			Examples:
				- Customer placed an order.
				- Payment completed.
				- User logged in.
				- Product added to cart.

		In simple words: An event represents an action or change that happened in a system.

		4. Streaming
			- Streaming means continuously sending and processing events as they happen.
			- Applications don't need to wait for all data to be collected.
			- Events can be processed in near real time.

		In simple words: Data keeps flowing continuously from producers to consumers.

		5. Final understanding:
			Apache Kafka = Open-source + Distributed + Event + Streaming

			- Open-source → Freely available source code.
			- Distributed → Runs across multiple servers.
			- Event → Records of things that happened.
			- Streaming → Continuously processes events in real time.

		One-line definition:
			Apache Kafka is an open-source platform that runs across multiple servers and allows applications to continuously 
			publish, store, and process events in real time. 
			

3--> Apache Kafka – Restaurant Analogy
     --> Imagine a restaurant where Cashier, Chef, Manager and Waiter work together.

		Workflow:
			1. Cashier (Producer):
				- Takes the customer's order.
				- Sends the order details to Kafka.

			2. Kafka (Messaging Platform):
				- Receives and stores the order.
				- Makes the order available to multiple departments.

			3. Chef (Consumer 1):
				- Reads the order from Kafka.
				- Prepares the food.

			4. Manager (Consumer 2):
				- Reads the same order.
				- Updates sales and order records.

			5. Waiter (Consumer 3):
				- Reads the order status.
			- Serves the food when it is ready.

		
		Mapping with Kafka:
			- Cashier → Producer (Sends messages)
			- Order Details → Event / Message
			- Order Register → Topic (Stores messages)
			- Kafka Server → Broker
			- Chef → Consumer
			- Manager → Consumer
			- Waiter → Consumer

		Why do we need Kafka?
			Suppose the cashier receives 100 orders.
				- The cashier doesn't need to contact each department separately.
				- The cashier publishes orders to Kafka.
				- Chef, Manager and Waiter can independently consume those events.
				- If the manager is temporarily unavailable, Kafka retains the messages so they can be processed later.

		Important:
			Kafka acts as a central messaging system that allows multiple applications (consumers) 
			to receive and process events independently without directly communicating with each other.
			

4--> Why do we use Apache Kafka?
     -->
		1. Decoupling Services
			- Services don't need to communicate directly with each other.
			- Producer sends events to Kafka, and consumers independently receive them.
			- If one consumer is down, other services can continue working.

		Example: Cashier sends an order to Kafka. Chef, Manager and Waiter independently receive the order without the cashier contacting each person.

		2. Scalability
			- Kafka can handle increasing amounts of messages by adding more brokers and partitions.
			- We can also add more consumers to process messages faster (within consumer group partition limits).

		Example: If a restaurant receives 100 orders instead of 10, we can add more chefs to handle the workload.

		3. Replayability
			- Kafka stores messages for a configured retention period.
			- Consumers can read old messages again by resetting their offsets.
			- Useful when we need to reprocess data or recover from errors.

		Example: If the manager's system crashes, it can read previously stored orders again after restarting.

		4. Efficiency
			- Kafka handles a large number of messages with high throughput.
			- Multiple consumers can process events independently.
			- Producers don't have to wait for every consumer to finish processing.

		Example: Cashier submits an order once, while Chef, Manager and Waiter process it independently.

		5. Quick Revision

		| Feature       | Meaning                                    |
		| ------------- | ------------------------------------------ |
		| Decoupling    | Services work independently.               |
		| Scalability   | Handle increasing workloads.               |
		| Replayability | Read and process old messages again.       |
		| Efficiency    | Process large volumes of messages quickly. |

		Remember: Kafka makes communication between microservices independent, scalable, reliable and efficient.
		

5--> What is Event Streaming?
     -->
		Event Streaming means continuously capturing data (events) in real time, 
		storing them in a log, and allowing systems to react to that data either immediately or later.

		Breaking it down:
		1. Continuously Capturing Data:
			- Continuously collects events as they happen.
			- Example: Customer places an order, payment is completed, user logs in.

		2. In Real Time:
			- Events are captured and made available almost immediately.
			- Applications don't need to wait for batch processing.

		3. Storing Them in a Log:
			- Events are stored in an ordered, persistent log (Kafka Topic).
			- Messages remain available for a configured retention period.

		4. React Immediately or Later:
			- Consumers can process events immediately or read them later.
			- They can also replay old events when required.

		Example (Restaurant):
			- Cashier receives a customer order.
			- The order event is immediately sent to Kafka.
			- Chef receives it and starts preparing food.
			- Manager can read the same order later to update sales records.

		Remember: Event Streaming = Continuously capturing + Storing + Processing events in real time or later.
		
6--> Different Communication / Data Processing Methods
    -->

		| Method             | Description                                                                                                       | Example                                                                        |
		| ------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
		| Request / Response | One service sends a request and waits for an immediate response.                                                  | REST API – Fetch user details.                                                 |
		| Batch Processing   | Collects data over a period and processes it together at scheduled intervals.                                     | Processing all daily bank transactions at midnight.                            |
		| Message Queue      | Sender puts messages into a queue, and consumers process them, generally one message at a time per consumer.      | Order service sends an order to a payment service through RabbitMQ.            |
		| Event Streaming    | Continuously captures, stores and distributes events so multiple consumers can process them immediately or later. | Kafka – Order events consumed by payment, notification and inventory services. |

		Quick Revision:
			1. Request/Response → Request and wait for response.
			2. Batch Processing → Collect first, process later.
			3. Message Queue → Send messages through a queue.
			4. Event Streaming → Continuously capture, store and process events.
			
7--> Kafka is like a WhatsApp group- Explanation:
     -->
		Imagine Kafka is like a WhatsApp group.
			1. Producer: A person who sends a message to the WhatsApp group.
			2. Kafka Topic: The WhatsApp group where messages are posted.
			3. Broker: The WhatsApp server that manages and stores messages.
			4. Consumer: Group members who receive and read messages.
			5. Event: The actual message sent to the group.

		Example:
			Imagine an e-commerce WhatsApp group called `Order Updates`.
			- Order Service (Producer) sends: "New Order Placed – Order #101".
			- Kafka (Topic) stores this event.
			- Payment Service (Consumer) reads the event and processes payment.
			- Inventory Service (Consumer) reads the same event and updates stock.
			- Notification Service (Consumer) reads the event and sends confirmation.

		Why is this useful?
			- One producer can send an event.
			- Multiple consumers can receive the same event.
			- Consumers work independently.
			- If a consumer is offline, it can read stored events later (within the retention period).

		Important difference from WhatsApp:
			Kafka is not just a messaging application. It is a distributed event streaming platform that stores events in an ordered log, 
			supports high message throughput and allows consumers to replay old events.

		Remember: Producer sends → Kafka stores → Consumers read and process.
		
8--> Apache Kafka vs RabbitMQ
     --> 
		Both Kafka and RabbitMQ are messaging systems used for communication between applications and microservices, 
		but their message storage and processing mechanisms are different.

		| Feature         | Apache Kafka                                                                     | RabbitMQ                                                                                  |
		| --------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
		| Model           | Distributed event streaming platform.                                            | Message broker based on queues.                                                           |
		| Message Storage | Stores messages in an ordered, persistent log for a configured retention period. | Stores messages in queues until they are acknowledged and removed (or otherwise handled). |
		| Consumer        | Multiple consumer groups can independently read the same events.                 | Messages are generally delivered to one consumer among competing consumers of a queue.    |
		| Persistence     | Messages remain available even after consumption, until retention expires.       | Messages can be persisted, but are generally removed after successful acknowledgement.    |
		| Ordering        | Maintains order within a partition.                                              | Maintains queue order, but multiple consumers and requeuing can affect processing order.  |
		| Throughput      | Very high throughput; suitable for large volumes of events.                      | Good throughput; suitable for flexible message routing and task queues.                   |
		| Best For        | Event streaming, real-time analytics, microservices event distribution.          | Task queues, background jobs, request processing and message routing.                     |

		Simple Example:
			Kafka: WhatsApp Group Analogy
				- Producer sends an order event.
				- Kafka stores the event.
				- Payment, Inventory and Notification services can independently read the same event.
				- Events can be read again later.

			RabbitMQ: Task Assignment Analogy
				- Producer sends an order-processing task to a queue.
				- RabbitMQ delivers the task to an available consumer.
				- Consumer processes the task and acknowledges it.
				- After acknowledgement, the message is normally removed from the queue.

		In Short:
			- Kafka → Event streaming + Persistent log + Replayability + High throughput.
			- RabbitMQ → Message queue + Flexible routing + Task distribution + Acknowledgement.

		Remember: Choose Kafka when you want to store and distribute streams of events to multiple independent consumers. 
		          Choose RabbitMQ when you want to distribute tasks or messages to workers for processing.
				  
				  
				  
				  
9--> Apache Kafka – Architecture and Components
     --> 

		1. Kafka Architecture
			Kafka follows a Producer → Broker → Consumer architecture.

			Basic Flow:
			1. Producer sends events to Kafka.
			2. Kafka stores events inside Topics.
			3. Topics are divided into Partitions.
			4. Consumers read events from Partitions.
			5. Consumer Groups allow multiple consumers to process events in parallel.

		2. Kafka Components

				1. Event (Message)
					- An event represents something that happened in an application.
					- It is the actual data sent from Producer to Kafka.
					- Examples: OrderCreated, PaymentCompleted, UserRegistered.

				2. Producer
					- Producer sends events to Kafka.
					- It decides which Topic to send the event to.
					- Example: Order Service sends an OrderCreated event to Kafka.

				3. Consumer
					- Consumer reads events from Kafka Topics.
					- It processes the received events.
					- Example: Payment Service consumes OrderCreated and processes payment.

				4. Topic
					- A Topic is a logical category where Kafka stores events.
					- Producers publish events to Topics.
					- Consumers subscribe to Topics.
					- Examples: order-topic, payment-topic, notification-topic.

				5. Partition
					- A Topic is divided into multiple Partitions.
					- Each Partition is an ordered, append-only log of events.
					- Partitions allow Kafka to process messages in parallel.
					- Each event gets a unique sequential Offset within its Partition.

					Example: 
						Topic: order-topic
						
							Partition 0: E1 → E2 → E3 → E4

							Partition 1: E5 → E6 → E7 → E8

							Partition 2: E9 → E10 → E11 → E12

					Important:
						- Ordering is guaranteed within a Partition, not across all Partitions.
						- Kafka uses a message key to determine the Partition (when a key is provided).

				6. Consumer Group
				    ########Very Important Lines###############
					- A Consumer Group is a group of consumers working together to process messages from a Topic.
					- Each Partition can be assigned to only ONE consumer within the same Consumer Group at a time.
					- Different Consumer Groups can independently consume the same Topic.

					Example:
						Topic: order-topic (3 Partitions)

							Consumer Group A:

							- Consumer 1 → Partition 0
							- Consumer 2 → Partition 1
							- Consumer 3 → Partition 2

							Consumer Group B:

							- Consumer 1 → Partition 0
							- Consumer 2 → Partition 1
							- Consumer 3 → Partition 2

					Important:
					########Very Important Lines###############
						- If a Topic has 3 Partitions, a Consumer Group can actively use a maximum of 3 consumers for that Topic.
						- Additional consumers remain idle for that Topic.
						

				7. Offset
					- Offset is a sequential position number assigned to each event within a Partition.
					- Consumers use offsets to track their reading progress.
					- Kafka stores committed offsets for each Consumer Group.

					Example:

						Partition 0:
							Offset:  0 → 1 → 2 → 3 → 4
							Event:   E1 → E2 → E3 → E4 → E5

						If a Consumer has processed up to Offset 2, it can continue reading from Offset 3.

					Important:
					########Very Important Lines###############
						- Offsets are maintained separately for each Partition and Consumer Group.
						- Consumers can reset offsets to read old messages again, provided messages are still retained.

				
				8. Consumer Rebalancing
					- Consumer Rebalancing means redistributing Partitions among consumers in a Consumer Group.
					- It happens when consumers join, leave, crash or when Topic partitions change.

						Example:

						Initially:

						- Consumer 1 → Partition 0, Partition 1
						- Consumer 2 → Partition 2

						After Consumer 3 joins:

						- Consumer 1 → Partition 0
						- Consumer 2 → Partition 1
						- Consumer 3 → Partition 2

						Kafka redistributes Partitions among available consumers.




		3. Quick Revision
		
			| Component      | Meaning                                   |
			| -------------- | ----------------------------------------- |
			| Event          | Actual message or record                  |
			| Producer       | Sends events                              |
			| Consumer       | Reads events                              |
			| Topic          | Logical category for events               |
			| Partition      | Divides Topic for parallel processing     |
			| Consumer Group | Consumers sharing workload                |
			| Offset         | Position of an event in a Partition       |
			| Rebalancing    | Redistributing Partitions among consumers |

		4. Important Rules to Remember

			1. Producer sends events to Topics.
			2. Topics contain one or more Partitions.
			3. Each Partition maintains its own event order.
			4. Each event has an Offset within its Partition.
			5. One Partition can be assigned to only one Consumer within a Consumer Group at a time.
			6. Different Consumer Groups can independently read the same events.
			7. Consumer Rebalancing redistributes Partitions when group membership or Topic assignments change.
			8. More Partitions allow more parallel processing, but ordering is maintained only within each Partition.
			
			
			
			
10--> Apache Kafka – Additional Components

		1. ZooKeeper
			- ZooKeeper was traditionally used by Kafka to manage and coordinate the Kafka cluster.
			- It maintained information about Brokers and their status.
			- It helped with controller election and cluster coordination.
			- It monitored Broker availability.

		Example:
			- Suppose Kafka has 3 Brokers.
			- If one Broker goes down, ZooKeeper helps Kafka detect the change and coordinate cluster management.

		Important:
			- Newer Kafka versions support KRaft mode, which replaces ZooKeeper.
			- ZooKeeper is not required when Kafka runs in KRaft mode.

		2. Broker
			- A Broker is a Kafka server that receives, stores and serves messages.
			- A Kafka cluster consists of one or more Brokers.
			- Each Broker manages Topic Partitions.
			- Brokers communicate with each other to manage replicated data.

			Example:
				Kafka Cluster:

				- Broker 1 → Partition 0
				- Broker 2 → Partition 1
				- Broker 3 → Partition 2

			Important:
				- Multiple Brokers provide scalability and fault tolerance.
				- If a Partition is replicated, another Broker can maintain its replica.

		3. Cluster
			- A Kafka Cluster is a group of Brokers working together.
			- It manages message storage, distribution and replication.
			- It provides scalability and fault tolerance.

			Example:
				Kafka Cluster
					|
					|---- Broker 1
					|---- Broker 2
					|---- Broker 3

			Important:
				- A single Broker can run Kafka independently.
				- Multiple Brokers work together to form a distributed Kafka Cluster.

		4. Producer Instance
			- A Producer Instance is an individual running instance of a Producer application.
			- It sends events to Kafka Topics.
			- Multiple Producer Instances can send events to the same Topic simultaneously.

			Example:
				- Order Service Instance 1 sends OrderCreated events.
				- Order Service Instance 2 also sends OrderCreated events.
				- Both send events to Kafka's order-topic.

			Important:
				- Multiple Producer Instances help generate events in parallel.
				- Producers do not need to know which Consumer will process their events.

		5. Consumer Instance
			- A Consumer Instance is an individual running instance of a Consumer application.
			- It reads and processes events from Kafka Topics.
			- Multiple Consumer Instances can work together within the same Consumer Group.

			Example:
				Topic: order-topic (3 Partitions)

				Consumer Group: payment-group

				- Consumer Instance 1 → Partition 0
				- Consumer Instance 2 → Partition 1
				- Consumer Instance 3 → Partition 2

			Important:
				- Each Partition is assigned to only one Consumer within the same Consumer Group at a time.
				- Multiple Consumer Instances allow parallel processing.
				- If one Consumer Instance crashes, Kafka can rebalance Partitions among the remaining consumers.

		6. Quick Revision

			| Component         | Meaning                                          |
			| ----------------- | ------------------------------------------------ |
			| ZooKeeper         | Traditionally manages Kafka cluster coordination |
			| Broker            | Kafka server that stores and serves messages     |
			| Cluster           | Group of Kafka Brokers                           |
			| Producer Instance | Individual running Producer application          |
			| Consumer Instance | Individual running Consumer application          |

		7. Important Difference

			- Broker → Part of Kafka infrastructure; stores and manages events.
			- Producer Instance → Application instance that sends events.
			- Consumer Instance → Application instance that reads events.
			- ZooKeeper → Older Kafka cluster coordination mechanism.
			- Cluster → Multiple Brokers working together.

		Remember: Producers send events → Brokers store events → Consumers process events. 
		          ZooKeeper traditionally helped manage the Kafka cluster, while newer Kafka deployments can use KRaft instead.
				  
				  

11--> Confusions????
      -->

		1. Sabse pehle: Kya Broker 1, 2, 3 independent hain?
			Haan, teeno independent Kafka Server instances hain, lekin ye ek hi Kafka Cluster ka part hain.
			Matlab:
				- Broker 1 = Kafka Server 1
				- Broker 2 = Kafka Server 2
				- Broker 3 = Kafka Server 3

			Ye milkar ek Kafka Cluster banate hain.

		2. Kya teeno Brokers mein same Topic hota hai?
			Yahan important difference samajhiye: Maan lijiye humne Kafka mein ek Topic banaya:
			`order-topic`

			Is Topic ko humne 3 Partitions mein divide kiya:
				- Partition 0
				- Partition 1
				- Partition 2
			Ab Kafka in Partitions ko different Brokers par distribute kar sakta hai.
			
			Replication Factor = 1 (No additional replicas)

				Kafka Cluster
				│
				├── Broker 1
				│     └── order-topic → Partition 0
				│
				├── Broker 2
				│     └── order-topic → Partition 1
				│
				└── Broker 3
					  └── order-topic → Partition 2
			
			Notice:
				- Teeno Brokers par same Topic ka data logically distributed hai.
				- Lekin har Broker ke paas alag Partition hai.
				- Is example mein koi replica nahi hai.

		3. Ab Replication Factor = 2 samajhiye
			Ab hum chahte hain ki agar koi Broker crash ho jaye, toh data available rahe.
			Isliye Kafka har Partition ki ek additional copy doosre Broker par rakhega.

				Kafka Cluster
				│
				├── Broker 1
				│     ├── P0 (Leader)
				│     ├── P1 (Replica)
				│     └── P2 (Replica)
				│
				├── Broker 2
				│     ├── P1 (Leader)
				│     ├── P2 (Replica)
				│     └── P0 (Replica)
				│
				└── Broker 3
					  ├── P2 (Leader)
					  ├── P0 (Replica)
					  └── P1 (Replica)

			Ab dekhiye:
				- Broker 1 ke paas P0 ki original copy aur P1, P2 ki replica copies hain.
				- Broker 2 ke paas P1 ki original copy aur P0, P2 ki replica copies hain.
				- Broker 3 ke paas P2 ki original copy aur P0, P1 ki replica copies hain.

			Matlab teeno Brokers par same Topic ki saari Partitions ki copies available hain.

		4. Agar Broker 1 crash ho gaya toh?
			Suppose Broker 1 ke paas P0 Leader hai.

			Agar Broker 1 crash ho gaya:

			- Broker 2 ke paas P0 ki replica already available hai.
			- Kafka eligible in-sync replica ko P0 ka naya Leader bana sakta hai.
			- Producers aur Consumers naye Leader se communicate kar sakte hain.

			Isse fault tolerance milti hai.

		5. Final confusion clear
			| Question                                   | Answer                                                      |
			| ------------------------------------------ | ----------------------------------------------------------- |
			| Are Brokers independent?                   | Yes, separate Kafka Server instances.                       |
			| Are they part of the same Cluster?         | Yes.                                                        |
			| Is the same Topic present across Brokers?  | Its Partitions are distributed across Brokers.              |
			| Does every Broker contain every Partition? | Only if replication placement puts a copy there.            |
			| Why replication?                           | To protect data and provide availability if a Broker fails. |

			Ek line mein yaad rakhiye:
				Topic ek hai, uski multiple Partitions hain, aur Kafka un Partitions ko different Brokers par distribute karta hai. 
				Replication enable karne par un Partitions ki copies bhi doosre Brokers par rakhi jaati hain.
				
				
				
				
11--> Clearity Now
      --> 
		Actually, Consumer ko manually har Broker se connect karne ki zarurat nahi hoti. 
		Kafka internally manage karta hai ki Consumer kis Broker se data read karega.
		Chaliye example se samajhte hain.

		1. Suppose our Kafka Cluster

			Humare paas:
				- 3 Brokers
				- 1 Topic: `order-topic`
				- 3 Partitions
				- Replication Factor = 2

			Kafka Cluster
				Broker 1          Broker 2          Broker 3
				--------          --------          --------
				P0 (Leader)       P0 (Replica)       P0 (Replica)
				P1 (Replica)      P1 (Leader)        P1 (Replica)
				P2 (Replica)      P2 (Replica)       P2 (Leader)
			

		2. Consumer data kaise read karta hai?
			Suppose Consumer Group mein 3 Consumer Instances hain.
				Consumer Group: order-group

				Consumer 1 → Partition 0
				Consumer 2 → Partition 1
				Consumer 3 → Partition 2

			Ab important point:
				- Consumer 1 ko Partition 0 read karna hai.
				- Partition 0 ka Leader Broker 1 hai.
				- Isliye Consumer 1 Broker 1 se data read karega.

			Similarly:
				- Consumer 2 → Broker 2 se Partition 1 read karega.
				- Consumer 3 → Broker 3 se Partition 2 read karega.

			Consumers normally Partition ke Leader se data read karte hain, replicas se nahi.

		3. Agar Broker 1 crash ho gaya toh?

			Suppose Broker 1 crash ho gaya.
				- Partition 0 ki replica Broker 2 aur Broker 3 par available hai.
				- Kafka eligible in-sync replica ko new Leader elect karega.
				- Suppose Broker 2 new Leader ban gaya.
				- Consumer 1 ab Broker 2 se Partition 0 read karega.

			Ye process Kafka automatically manage karta hai.

		4. Final Understanding
			- Producer → Kafka Broker ke through event publish karta hai.
			- Broker → Events ko Partitions mein store karta hai.
			- Consumer → Assigned Partition ke Leader Broker se events read karta hai.
			- Replicas → Leader Broker fail hone par backup provide karti hain.
			- Kafka → Leader election, metadata aur partition assignment manage karta hai.

		Remember: Consumer ko ye manually decide nahi karna hota ki kis Broker se connect hona hai. 
		          Kafka metadata ke through Consumer ko correct Broker aur Partition ki information milti hai.
				  
				  
				  

12--> Configurations of below points jab Topic banate tabhi karte-
      -->
		1. Number of Partitions
		2. Replication Factor
		3. Number of Brokers (cluster setup ke time)

			1. Number of Partitions kaise decide karte hain?
				Partitions decide karte hain ki Topic ka data kitne parts mein divide hoga.

				Example:
					kafka-topics.sh --create \
					  --topic order-topic \
					  --bootstrap-server localhost:9092 \
					  --partitions 3 \
					  --replication-factor 2

				Here:
					- `--partitions 3` → Topic mein 3 Partitions hongi.
					- `--replication-factor 2` → Har Partition ki 2 copies hongi (1 Leader + 1 Replica).

				Kaise decide karein?
					- More Partitions → More parallel processing.
					- Fewer Partitions → Less parallel processing.
					- Partitions ki sankhya expected throughput aur maximum consumer parallelism ke according decide karte hain.

				Example: Agar 5 consumers ko parallel processing karwani hai, toh at least 5 Partitions chahiye (same Consumer Group ke liye).
				

			2. Replication Factor kaise decide karte hain?
				Replication Factor batata hai ki har Partition ki total kitni copies maintain hongi.

				Example:
					Replication Factor = 1
						- 1 Leader copy.
						- No additional replica.

					Replication Factor = 2
						- 1 Leader copy.
						- 1 Replica copy.

					Replication Factor = 3
						- 1 Leader copy.
						- 2 Replica copies.

				Kaise decide karein?
					- RF = 1 → Development/testing environments.
					- RF = 2 → Basic redundancy.
					- RF = 3 → Common production choice for better fault tolerance.

				Important: Replication Factor 3 ka matlab 3 additional copies nahi, balki total 3 copies hain.

			3. Number of Brokers kaise decide karte hain?
				Brokers ka number Kafka Cluster setup karte time decide karte hain.

				Example:
					Kafka Cluster

					Broker 1
					Broker 2
					Broker 3

				Kaise decide karein?
					- 1 Broker → Local development/testing.
					- 3 Brokers → Common production starting point.
					- More Brokers → Higher storage and processing capacity, depending on workload.

                ########Very Important Line###############
				Important: Replication Factor cannot be greater than the number of available Brokers.

			4. Complete Example
				Suppose we create:
					- Topic = `order-topic`
					- Partitions = 3
					- Replication Factor = 2
					- Brokers = 3

				Architecture:

							 order-topic
							 3 Partitions
								  |
					   -----------------------
					   |          |          |
					  P0         P1         P2
					   |          |          |
					Broker 1   Broker 2   Broker 3
					 Leader     Leader     Leader
					   |          |          |
					Broker 2   Broker 3   Broker 1
					 Replica    Replica    Replica
				
				

				| Configuration      | Value | Meaning                                  |
				| ------------------ | ----- | ---------------------------------------- |
				| Brokers            | 3     | Three Kafka servers                      |
				| Partitions         | 3     | Three data partitions                    |
				| Replication Factor | 2     | Two copies per partition                 |
				| Total replicas     | 6     | 3 × 2                                    |
				| Consumer instances | 3     | Can process all 3 partitions in parallel |

			5. Important Commands

			Create Topic:
				```
				kafka-topics.sh --create \
				  --topic order-topic \
				  --bootstrap-server localhost:9092 \
				  --partitions 3 \
				  --replication-factor 2
				```

			Describe Topic:
				```
				kafka-topics.sh --describe \
				  --topic order-topic \
				  --bootstrap-server localhost:9092
				```

			List Topics:
				```
				kafka-topics.sh --list \
				  --bootstrap-server localhost:9092
				```

			Remember:
				- Brokers → Kitne Kafka servers chahiye.
				- Partitions → Kitni divisions mein data process karna hai.
				- Replication Factor → Har Partition ki kitni copies maintain karni hain.

			One important point: Production mein Partition count aur Replication Factor randomly decide nahi karte. 
			                     Expected message volume, throughput, consumer parallelism, fault tolerance aur available storage ko consider karte hain.
